# Процесс разработки

Цель первого выпуска — воспроизводимая образовательная лаборатория, в которой наблюдения можно проверить, а художественный контекст не подменяет физику. Рабочий процесс хранится рядом с кодом; GitHub Issues служат карточками работы. Наличие этого документа не означает, что GitHub Project уже создан или настроен.

## Доска и правила движения

| Стадия | Вход и результат | WIP |
| --- | --- | --- |
| Backlog | Есть проблема, но ещё не выполнен Definition of Ready | Без лимита; сортировать по влиянию и риску |
| Ready | Задача готова к исполнению, проверки и зависимости известны | 6 карточек |
| Doing | Назначен исполнитель; есть текущая работа и следующий проверяемый результат | 4 карточки |
| Review | Реализация закончена; приложены доказательства, идёт независимая проверка | 2 карточки |
| Done | Все применимые проверки пройдены и результат принят | Без лимита |
| Blocked | Названы причина, владелец снятия блока и следующий шаг | 2 карточки; входит в общий WIP |

Общий WIP для Doing + Review + Blocked — не более 6. Сначала завершать Review и снимать блокировки, затем начинать новое. На одну карточку — один ответственный исполнитель; дополнительные агенты помогают с ограниченными независимыми частями. Превышение лимита допускается только с записанными причиной и сроком пересмотра в карточке.

Переходы: Backlog → Ready → Doing → Review → Done. Review → Doing возвращает работу с конкретным невыполненным критерием. Blocked — отдельное состояние с сохранением прежней стадии. Закрытие GitHub issue соответствует Done; открытая issue может находиться на любой другой стадии. В body карточки обязателен `Stage:`; если используется GitHub Project, его поле Status должно совпадать. Изменять оба источника в одном обновлении. Репозиторный [backlog](backlog.md) и компактный `docs/issues.json` — датированные снимки, а не независимая доска. Полные тела карточек хранятся только в GitHub Issues; снимки не требуют дублировать их при каждом изменении.

## Definition of Ready

- Описаны пользователь, конкретный вопрос или затруднение и ожидаемое наблюдаемое поведение.
- Есть границы работы, зависимости, сценарий демонстрации и критерии приёмки.
- Для научного утверждения указаны источник, допущения, единицы и граница применимости; для художественного мотива — книга и объяснение связи с опытом.
- Для интерфейса определены начало сценария, действие, обратная связь, состояния ошибки/паузы и текстовый эквивалент результата.
- Задача оценена независимо минимум в двух раундах или явно помечена как предварительная. Неопределённость выделена в короткое исследование, а не спрятана в оценку.
- Карточка 13 SP разделена на проверяемые срезы; срезы не означают дополнительные SP поверх оценки карточки.

## Planning poker

Шкала: **1, 2, 3, 5, 8, 13, 21**. Story points отражают относительный объём, сложность и риск проверки; это не часы и не обещание срока.

1. Автор объясняет пользовательскую проблему и критерии, но не предлагает оценку первым.
2. Исполнитель, научный рецензент и UX/QA оценивают независимо. Для агентного раунда оценки скрываются друг от друга до раскрытия; результаты маркируются «оценки агентов». Участие людей не заявляется, если его не было.
3. После одновременного раскрытия обсуждаются минимальная и максимальная оценки. Уточняются допущения и проводится второй раунд при существенном расхождении.
4. В issue сохраняются индивидуальные оценки, неопределённости и выбранная плановая оценка. Нельзя называть консервативный выбор консенсусом.
5. 21 SP означает необходимость декомпозиции до начала реализации. Такая карточка может оставаться родительской инициативой; в работу берутся только отдельно оценённые срезы, WIP не считает родителя второй раз. 13 SP допускается как родительская карточка только с независимыми критериями для срезов.

Первичный агентный раунд находится в [backlog](backlog.md). Плановые оценки предварительные; фактической скорости команды ещё нет, поэтому прогноз даты по сумме SP не строится.

## Исследование → issue → реализация → приёмка

Каждая существенная гипотеза связывается с исследованием, карточкой, кодом/PR, проверкой и демонстрацией. Формат записи:

`утверждение / пользовательская проблема → источник или наблюдение → GS-xx / GitHub issue → файлы и commit → команда или сценарий проверки → артефакт → решение рецензента`.

Исследование фиксирует дату доступа, прямую ссылку, что именно она подтверждает, допущения и оставшиеся вопросы. Предпочтительны первичные статьи, документация библиотек и университетские материалы. Поисковая выдача не является источником. Парафраз литературного мотива не выдаётся за цитату, научный факт или моделирование всей сцены романа.

## Независимая приёмка

Для пользовательской проверки выбирать роль P, сквозное условие C и задание T из [матрицы приёмки](research/acceptance-personas.md). Использовать [бланк наблюдения](acceptance/audience-pilot.md); результаты популярности служат основанием разнообразить набор, а не весами выборки. Техническое прохождение и понимание человеком фиксируются раздельно.

| Область | Рецензент и проверка | Доказательство |
| --- | --- | --- |
| Научная модель | Агент, не написавший ядро: формулы, единицы, пределы, эталоны и сходимость | Ссылки на источники и тесты; расхождения и пределы |
| Учебный сценарий | Агент, не написавший текст: путь новичка и путь исследователя | Вопрос → действие → наблюдение → вывод; точные места затруднений |
| UX и визуальная компоновка | Агент, не собравший проверяемый экран: реальные свежие скриншоты desktop/mobile | Файл, viewport, commit, шаг сценария; список дефектов по тяжести |
| E2E и доступность | Независимая проверка production build | Отчёт Playwright, keyboard-only, reduced motion, axe и ручные ограничения |

Агент не принимает собственную реализацию единолично. Перепроверять все основные области интерфейса: навигацию, учебный маршрут, модель, параметры, результаты, объяснения/источники, шаринг/сброс, ошибки и малый экран. Скриншот подтверждает компоновку, но не правильность физики или полную доступность. Прошедший unit-тест не заменяет пользовательский сценарий. При недостатке независимого рецензента сохранять Stage: Review с перечислением непроверенного.

## Решение о текущем релизе по RAPID

По поручению владельца продукта от 14 ноября 2026 года реальные интервью для этого выпуска заменены экспертными ролевыми прогонами субагентов. Это изменение метода приёмки, а не подтверждение пользовательских гипотез. Автор сценария не принимает собственную реализацию единолично; проверка на физических устройствах и с реальными людьми остаётся отдельным видом доказательства.

[RAPID](https://www.bain.com/insights/rapid-decision-making/) распределяет ответственность: один Recommend собирает рекомендацию; независимые Agree отвечают за научные и UX-требования; Perform реализует; Input предоставляет данные об аудитории и учебном применении; один Decide принимает итоговое решение в разрешённом объёме. Это распределение ролей не заменяет сами проверки и не является голосованием большинством.

[Решение и матрица покрытия](acceptance/rapid-decision.md) содержат точную сборку, фактические заключения, ограничения и результат. Для этого выпуска отсутствие интервью не блокирует согласованный экспертный релиз; оно блокирует заявления о доказанном учебном эффекте и предпочтениях реальных людей.

## Definition of Done

- Выполнены критерии карточки; научные числа происходят из модели, а не подписи режима.
- Пройдены применимые unit, typecheck, build и E2E на production build; команды и commit указаны в карточке/PR.
- Проведена независимая научная и/или UX-проверка по области изменения. Нет открытых P0/P1, мешающих сценарию или искажающих утверждения.
- Проверены клавиатура, адаптивная компоновка, пауза/сброс, ошибки и уменьшение движения, если они затронуты.
- Источники, допущения, пользовательская документация и demo script соответствуют поведению.
- Нет лишних интеграций, секретов, сломанных внешних ресурсов и шаблонных обещаний; сохранены лицензии и необходимые атрибуции.
- Доказательства приложены, рецензент записал решение. Issue закрывается только после этого; merge не равен автоматической приёмке.

## Выпуск и демонстрация

При аудите стоимости сопровождения считать отдельно production-код, тексты, тесты, генерируемые файлы и evidence; смотреть зависимости и повторяющиеся обязанности. Решение о готовой библиотеке должно учитывать адаптеры, сборку, обновления и регрессии, а не только LOC. Текущий [аудит по слоям](research/maintenance-cost.md) — обязательный вход RAPID для релиза.

Release gate обязателен для точного commit и артефакта сборки:

1. Чистая установка из lockfile; поддерживаемая версия Node; typecheck, unit и production build проходят.
2. E2E против production preview: первый опыт новичка, раскрытие исследовательского уровня, смена модели, измерение, пауза/шаг/сброс, восстановление состояния по ссылке.
3. Визуальная матрица: 1440×900, 768×1024 и 390×844; длинный русский текст, фокус, выбранные состояния, ошибка/останов и отсутствие горизонтального переполнения.
4. Проверка клавиатурой и автоматический accessibility scan; известные ограничения записаны, обещание полной WCAG-сертификации не делается.
5. Научные эталоны и инварианты подтверждены; пользователь видит пределы модели и различие факта, численного приближения и художественной идеи.
6. Артефакт работает без AI API и runtime CDN; список зависимостей, лицензии и audit разобраны. Непринятые риски блокируют выпуск.
7. Runbook содержит build/preview/deploy/rollback, целевую площадку и smoke check. Публикация и проверка доступного URL — отдельные действия; готовность артефакта не называется опубликованным релизом.
8. Записаны итог приёмки, известные ограничения, URL/версия артефакта и сценарий демо. Без живого URL допустимо только «локальное демо готово».

## Ритм работы

В начале рабочего цикла — проверить блокировки, готовность исследований и WIP. При каждом законченном срезе — обновить карточку и приложить доказательство. После независимой приёмки — короткая демонстрация и пересмотр backlog. Ретроспектива фиксирует один измеримый процессный дефект и одно изменение на следующий цикл. Нет автоматического расписания, ежедневных встреч или внешних уведомлений, пока их явно не настроили.

Измерять cycle time Ready → Done, возраст Doing/Review, время Blocked, число возвратов из Review и дефекты после выпуска. Не оценивать людей или агентов по числу закрытых карточек и не сравнивать SP разных команд.
